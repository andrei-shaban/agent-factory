## Executive Summary

«Фабрика агентов и алгоритмов» — универсальная платформа для перевода повторяющихся операций в управляемые сценарии, собранные из ИИ-агентов, детерминированных алгоритмов и точек человеческого контроля. Платформа предметно-независима: одинаково применима к потокам документов, согласованиям, отчётности и точечным задачам полного цикла. Смена предметной области не требует переделки ядра — достаточно описать новый сценарий, собрать команду агентов и подключить переиспользуемые библиотеки инструментов.

**Ключевой принцип** — автоматизация оправдана только там, где даёт измеримый результат: сокращает время, снижает ошибки, убирает рутину и сохраняет управляемость. Бизнес-логика и финансово значимые расчёты выполняются детерминированными алгоритмами и проходят проверку человеком; ИИ отвечает за понимание контекста, извлечение данных, подготовку черновиков и взаимодействие с оператором.

Роль разработчика смещена с инфраструктуры на содержание автоматизации. Платформа берёт на себя оркестрацию графов, хранение состояния, изоляцию недоверенного кода, доставку событий, аудит и интеграцию с локальными моделями. Разработчик описывает сценарий, собирает фабрику под задачу и разрабатывает переиспользуемые библиотеки инструментов. Архитектура гарантирует автономность в изолированном контуре, отсутствие зависимости от внешних облаков, строгое разделение данных и вычислений, контроль доступа, наблюдаемость каждого шага и сохранение состояния процессов на дни и недели.

## 1. Ключевые архитектурные принципы

### Полный Open Source и отсутствие Vendor Lock-in
* Отказ от проприетарных облачных платформ в пользу библиотеки `langgraph` и self-hosted решений.
* Открытые стандарты взаимодействия: протокол `AG-UI` (фронтенд ↔ бэкенд), OpenAI-совместимый API (локальные модели).
* Свежие стабильные ветки компонентов для предотвращения морального устаревания к моменту ввода в эксплуатацию.

### Работа в изолированном корпоративном контуре (Air-Gap)
* Полная автономность: отсутствие доступа в интернет, все зависимости из внутренних зеркал (Docker registry, PyPI, npm), образы зафиксированы по digest, внешние CDN и телеметрия отключены.
* Доверие к внутреннему УЦ: корпоративный Root CA вшит в базовые образы.
* Внутренние источники артефактов: песочницы получают зависимости опосредованно, через воркер.

### Архитектура «Фабрики» (Агенты + Алгоритмы + HITL)
* Гибридная оркестрация: в одном графе состояний объединяются недетерминированные вызовы LLM, детерминированные Python-алгоритмы и точки остановки для человека (**HITL**).
* Воркеры обращаются к корпоративным данным (мастер-данные, реестры) для бизнес-логики.
* Интерактивный UI в потоке: кастомные бизнес-формы (например, Diff-сравнение «источник vs исходник») встраиваются прямо в ленту диалога.

### Асинхронность и живучесть долгих сценариев
* Независимость от сессии браузера: выполнение вынесено в фоновые воркеры, события буферизуются в шине, состояние пауз HITL сохраняется в реляционной БД на дни и недели.
* Потоковая передача без потерь через SSE без буферизации и с длинными таймаутами.

### Корпоративная аутентификация и сквозной аудит
* Единый вход через связку Nginx + `oauth2-proxy` + Keycloak с федерацией LDAP/AD.
* Проброс идентификаторов пользователя и групп до уровня бэкенда и воркеров.
* Полный трейсинг шагов графа, расход токенов, логирование утверждений HITL; доступ к корпоративным данным логируется на стороне воркеров.

### Строгая сегментация и информационная безопасность
* Разделение контуров по узлам: периметр и observability (ВМ №1), вычисления, данные агентов и песочницы (ВМ №2), инференс и распознавание документов (GPU ендпоинты, узел №3), корпоративное хранилище данных (ВМ №4).
* Изоляция недоверенного кода: одноразовые контейнеры без доступа к сети, с read-only файловой системой и без доступа к секретам; исполняются выделенным rootless-демоном Docker с runtime `runsc`.
* Защищённые интеграции через **mTLS**: двусторонняя аутентификация при обращении к узлу инференса, серверу рабочей станции и корпоративному хранилищу данных. Ключи изолированы на вычислительном узле.

### Единообразие и простота эксплуатации
* **Single Image** для Python: API-шлюз и фоновый воркер собираются из одного образа с разными точками входа.
* Минимум лишних рантаймов в проде: фронтенд собирается в статику и раздаётся напрямую через Nginx; vendor-рантаймы UI (Copilot Runtime и аналоги) не используются.

### Принцип автономности артефактов
Docker-образы — статичные рантайм-контейнеры; в них не вшивается ничего, влияющее на автономность, безопасность и поведение системы. 

Код приложения, конфигурации, скрипты инициализации, криптографические материалы (корневые и серверные сертификаты, приватные ключи), зависимости, секреты и бизнес-данные поставляются и обновляются **отдельно от сборки образа** — через механизмы внешней поставки: bind-mount из хостовой системы, named volumes, внутренний артефакт-репозиторий, secrets manager. 

В образ допускается включать только базовый рантайм, минимальный набор системных пакетов, структуру директорий для монтирования и OCI-метаданные. 

Это обеспечивает раздельные жизненные циклы образа и артефактов, безопасную ротацию секретов без пересборки, единый образ для всех окружений и полную автономность в Air-Gap.

### Соответствие отраслевым стандартам безопасности
Проект разрабатывается в соответствии со стандартами: **OpenSSF Best Practices** (Open Source Security Foundation). Архитектура и процессы разработки следуют рекомендациям OpenSSF по безопасной разработке открытого программного обеспечения, включая: 
* Управление зависимостями и supply chain security (SBOM, digest pinning, сигнатуры образов).
* Изоляцию выполнения недоверенного кода (gVisor/runsc, rootless containers).
* Криптографическую защиту коммуникаций (mTLS, корпоративный Root CA).
* Наблюдаемость и аудит (OpenTelemetry, Langfuse), а также принципы минимальных привилегий и сегментации контуров.

Соответствие проверяется в чек-листах готовности к внедрению (§5).

## 3. Совместимость и обязательные параметры

### 3.1. Хранилища данных (PostgreSQL / Redis / S3)

**PostgreSQL — изоляция инстансами:**
* **ВМ №1 (Auth & Observability):** обслуживает исключительно базы Keycloak и Langfuse во внутренней сети контейнеров ВМ №1; внешний порт 5432 на хосте закрыт.
* **ВМ №2 (Runtime & RAG):** обслуживает чекпоинты LangGraph, реестр ранов фабрики и векторный поиск pgvector; размещён на отдельном дисковом томе с жёстким лимитированием памяти (`shared_buffers`, `work_mem`) для исключения конкуренции с Redis и песочницами; настроен регулярный бэкап (WAL-архивация / `pg_basebackup`) с репликацией на off-host инстанс (ВМ №1).
* **Параметры подключения:** `psycopg_pool`: `autocommit=True`, `row_factory=dict_row`, `prepare_threshold=0`; TLS + `scram-sha-256`. Gateway подключается отдельной ролью с правами только на реестр ранов (без доступа к чекпоинтам и RAG).
* **Корпоративные данные:** воркеры обращаются к отдельной СУБД PostgreSQL (ВМ №4) для чтения мета-данных и схем БД, мастер-данных, реестров и справочников. Доступ — mTLS (клиентский сертификат воркера, подписанный корпоративным CA), read-only (`SELECT`). Корп. PG не обслуживает runtime Фабрики (чекпоинты, реестр ранов — на ВМ №2).

**Идемпотентность и конкуренция (Runtime):**
* Один исполнитель треда: advisory-lock в PostgreSQL ВМ №2 на `thread_id`; повторный запуск рана из реестра после сбоя не создаёт параллельного исполнения.
* Каждая внешняя бизнес-операция (АРМ, корпоративные системы) несёт idempotency-key: дедуп-таблица в реестре ранов + проброс ключа в целевую систему; двойное утверждение HITL даёт ровно один эффект.
* `interrupt()` размещается в отдельной ноде графа: LangGraph реплеит ноду с начала, поэтому побочные эффекты в нодах с interrupt недопустимы.

**Redis — изоляция инстансами:**
Redis фабрики и Redis Langfuse — два отдельных контейнера. Логические БД не используются как граница изоляции: ACL Redis не ограничивают доступ по номеру `db`. Изоляция обеспечивается отдельными инстансами и ACL-пользователями (`agui_svc`, `langfuse_svc`).

* **Redis — фабрика (ВМ №2):** размещён локально к воркеру-продюсеру для минимизации round-trip при `XADD` на каждое событие. Шлюз ВМ №1 подключается по TLS с ACL-пользователем `agui_svc` и читает `XREAD BLOCK ... COUNT` с таймаутом 10 с и TCP keepalive. `appendonly yes`, `appendfsync everysec`, AOF на томе, отдельном от томов SeaweedFS и PostgreSQL.
  * Раскладка ключей: отдельный Stream на ран (`run:{id}:events`), жёсткий `MAXLEN ~ N` per-run.
  * TTL на ключ Stream на горизонт HITL-паузы (30 дней) и продлевается при активности; TTL не должен уничтожать буфер приостановленного треда.
  * Реконнект после трима буфера: сначала подписка на живой хвост, затем чтение снапшота из чекпоинта, дедупликация по Stream ID.
  * ACL без админ-команд, с `+@blocking` (`XREAD BLOCK` шлюза, `BRPOP` брокера TaskIQ).
* **Redis — Langfuse (ВМ №1):** `maxmemory-policy noeviction` (требование BullMQ); ACL допускает Lua-скрипты и блокирующие команды, необходимые очереди инжеста.

**SeaweedFS:**
* S3 port 8333, path-style, TLS; отдельный том.
* Отдельные S3-identity с правами по бакетам: Langfuse (blob), воркер (артефакты агентов, Diff-файлы), backup (запись бэкапов).
* Критичные бакеты (бэкапы PG, WAL) реплицируются на второй инстанс SeaweedFS на ВМ №1: потеря ВМ №2 не уничтожает бэкапы.

### 3.2. Безопасность и изоляция (Sandbox / mTLS / Air-Gap)

* **Sandbox & Docker Socket Proxy:** песочницы исполняются выделенным rootless-демоном Docker (`default-runtime=runsc`, userns); socket-proxy смотрит только на сокет этого демона, сокет основного демона не публикуется нигде. Прокси фильтрует метод+путь, но не тело запроса — изоляция обеспечивывается **выделенным демоном**, а не флагами прокси. Whitelist прокси: `CONTAINERS=1`, `POST=1`, `ALLOW_START=1`; `EXEC`, `IMAGES`, `NETWORKS`, `VOLUMES` и остальные секции запрещены. Параметры контейнеров: `runsc`, `--network none`, read-only rootfs, tmpfs, `cap-drop ALL`, `no-new-privileges`, лимиты CPU/memory/pids; секреты внутрь не передаются.
* Песочницы не имеют сетевого доступа ни к Redis, ни к S3, ни к зеркалу PyPI; зависимости и данные доставляются воркером через локальные тома.
* **Поставка библиотек в песочницы:** основной путь — предзапечённые toolset-образы с фиксированными версиями. Для динамических зависимостей воркер загружает wheels из внутреннего зеркала PyPI (ВМ №1) в локальный wheel-cache на ВМ №2; песочница устанавливает пакеты из этого каталога, смонтированного read-only: `pip install --no-index --find-links /cache --no-cache-dir --require-hashes --target /tmp/deps` (tmpfs) + `PYTHONPATH=/tmp/deps`. Состав кэша фиксируется хешами и проверяется перед установкой.
* **mTLS-интеграции:** клиентские сертификаты воркера подписаны корпоративным CA; используются при обращении к узлу инференса (GPU ендпоинты), серверу рабочей станции и корпоративному хранилищу данных (ВМ №4). Ключи изолированы исключительно на ВМ №2.
* **Air-Gap:** образы pinned by digest из внутреннего Docker registry; зависимости из внутренних зеркал (PyPI, npm); CDN запрещён; телеметрия отключена.
* **MCP:** не входит в базовый стек; подключается только как опциональный адаптер по условиям §6.2.

### 3.3. Интеграция с моделями (GPU ендпоинты)

* **Эндпоинты инференса:** единая точка входа — nginx GPU-узла по 443 с mTLS; бэкенды во внутренней сети, прямых обращений к ним нет.
* **LLM:** маршрут `/`, OpenAI-совместимый API — `/v1/chat/completions`, `/v1/models`, служебные `/props`, `/slots`.
* **Эмбеддинги:** отдельный инстанс `llama-server` с `--embeddings`, `/v1/embeddings`.
* Имя модели берётся автообнаружением через `/v1/models` (строка алиаса чувствительна к точному написанию).
* Обязателен потоковый режим `stream: true` при длинных генерациях; продуктовый лимит ответа задаётся `max_tokens` в теле запроса.
* **Эндпоинт распознавания:** маршрут `/ocr/`, метод POST, `Content-Type: application/json`, тело `{file, fileType}` — `file` содержит base64 (URL-вариант не используется: в Air-Gap нет маршрута GPU → S3), `fileType`: 0 = PDF, 1 = изображение (включая многостраничный TIFF). Multipart не поддерживается; лимит тела на шлюзе 20M с учётом base64-накладных (+33%), что соответствует 15 МБ исходного файла на запрос: многостраничные документы воркер режет на страницы/батчи и собирает результат. Ответ — `result.layoutParsingResults[]` по числу страниц: `markdown.text` и `prunedResult` с геометрией регионов. Обязательные поля запроса: `visualize: false`, `returnMarkdownImages: false`.

### 3.4. Сетевой периметр и аутентификация

* **nginx SSE (ВМ №1):** `proxy_buffering off`, `proxy_http_version 1.1`, `proxy_read_timeout 3600s`, `X-Accel-Buffering: no`.
* **SSE heartbeat:** комментарий-keepalive каждые 15 с, чтобы idle-стримы не рвались по таймаутам промежуточных прокси.
* **Auth:** `X-Forwarded-User/Groups` только из `auth_request_set`; Keycloak group mapper; oauth2-proxy `set-xauthrequest`; SPA обрабатывает 401 редиректом.
* **Langfuse:** инжест — отдельный `server_name` на 443 без oauth2-proxy, mTLS клиентским сертификатом воркера; UI Langfuse — через периметр с OIDC-федерацией Keycloak (без отдельных паролей).

### 3.5. Протокол AG-UI

* Протокол [AG-UI](https://docs.ag-ui.com/introduction?spm=a2ty_o01.29997173.0.0.3ddcc92144tFQf) (Agent-User Interaction) — открытый стандарт для событийного взаимодействия фронтенда и агентного бэкенда. Пин `ag-ui-protocol` зафиксирован на версии `1.0.0`. Зависимость `ag-ui-langgraph==0.0.47` проверена на совместимость с этим протоколом. Добавлен модуль `ag-ui-a2ui-toolkit==0.0.6` для расширения интерфейсных возможностей. Адаптер исполняется в воркере; Gateway только ставит задачи и отдаёт SSE.
* SPA подключается к Gateway напрямую через `@assistant-ui/react-ag-ui` поверх `HttpAgent` (`@ag-ui/client` ≥1.0.3), без vendor-рантайма. Interrupts в AG-UI-адаптере assistant-ui имеют experimental-статус — приёмка обязательна на эталонном графе (§5.6).
* Реконнект `Last-Event-ID` + снапшот/живой хвост реализуется тонкой прослойкой клиента поверх `HttpAgent` (готовые клиенты эту семантику из коробки не реализуют).

### 3.6. Базовый рантайм и наблюдаемость

* **Единый Python-образ:** Gateway и Worker собираются из одного образа с разными entrypoints: `uvicorn` / `taskiq worker`.
* **Python 3.14:** используется как основной рантайм. Все критические бинарные зависимости (`psycopg-binary`, `cryptography`, `hiredis`) собраны под эту версию в текущем окружении. Корпоративный Root CA в образе; `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt`.
* **Стек воркера:** `langgraph` 1.2.24, `langgraph-checkpoint-postgres` 3.2.1, `taskiq` 0.13.0, `taskiq-redis` 1.2.4, `psycopg[binary,pool]` 3.3.9, `httpx` 0.28.1.
* **Стек Gateway:** FastAPI 0.165.0, uvicorn 0.54.0, `ag-ui-protocol` 1.0.0.
* **Langfuse:** сервер v4 (пин v4.82+, минимум 4.59.0) — обязательное требование Python SDK v5; серверной линии 5.x не существует. Клиентский SDK — `5.2.0`. Инжест — OTel-эндпоинт `/api/public/otel/v1/traces` (legacy `/api/public/ingestion` на v4 в events_only-режиме отклоняется). Трейсы уходят асинхронно по HTTP.

### 3.7. Манифесты

#### 3.7.1. Общие положения

* Манифесты алгоритмов и сценариев — **файлы рядом с кодом**, поставляемые на ВМ №2 как артефакты через bind-mount (принцип автономности артефактов, §1). Редактируются в репозитории и являются единственным источником истины по контракту.
* Воркер читает манифесты напрямую из файлов и строит in-memory индекс при старте; отдельной базы данных и каталога для манифестов в платформе нет.
* Пара `(id, version)` immutable; изменение — только новой версией.
* Список сценариев для SPA — лёгкий генерируемый артефакт `scenarios.json` (`id`, `version`, `access_group`, описание). Генерируется из манифестов при развёртывании и раздаётся nginx ВМ №1 как статика; SPA фильтрует его по группам пользователя для отображения (это только UX). Принуждение — на воркере (§3.7.2).
* Запись рана хранит `id + version + digest файла манифеста` — аудит «какая версия исполнялась». Digest считается при развёртывании/загрузке воркером.
* Манифест не заменяет язык оркестрации: исполнимая реализация графа — код на LangGraph; манифест декларирует узлы, порядок и условия ветвления, контракты; CI сверяет манифест с графом в обе стороны (узлы и рёбра существуют, `ref` резолвятся по точным версиям, схемы валидны).
* Совместимость без внедрения: блок для модели отображается на MCP tool-descriptor и аннотации; описательная часть — на конвенции SKILL.md. MCP и Agent Skills не внедряются (§6).

#### 3.7.2. Контекст пользователя и видимость манифестов

* Аутентификация пользователя выполняется через Keycloak с федерацией LDAP/AD; группы маппятся в клейм и пробрасываются до Gateway и воркера.
* Воркер исполняет ран в пользовательском контексте: principal-контекст сохраняется в записи рана и используется при сборке LLM-контекста.
* Видимость сценариев и публичных алгоритмов определяется AD-группами: `access_group ∈ групп пользователя`.
* По умолчанию группа сценария именуется по конвенции `fab-{scenario_id}`; манифест может переопределить `access_group`.
* Перед сборкой контекста модели воркер строит allowlist разрешённых манифестов; запрещённые сценарии и алгоритмы модели не подаются и для неё не существуют (минимальная осведомлённость).
* Запуск, резюм сценария и вызов публичного алгоритма проверяются детерминированно на воркере; отказ фиксируется в аудите. Модель не принимает решение о доступе: доступ применён до неё.
* Внутренние алгоритмы сценария (`visibility: internal`) не публикуются в общем списке и доступны только в составе разрешённого сценария, который их объявляет.
* Инференс на GPU-ендпоинты остаётся system-to-system mTLS с системным сертификатом; пользовательская авторизация не подменяет системные сертификаты и не передаётся на инференс как механизм аутентификации.
* Администрирование доступов выполняется только в AD/Keycloak; отдельный админ-интерфейс платформы не реализуется.

#### 3.7.3. Манифест алгоритма — состав

| Блок | Поля | Обяз. | Кто читает |
| --- | --- | --- | --- |
| Идентичность | `id`, `version` (semver), `kind: algorithm`, `owner`, `lifecycle: active\|deprecated`, `supersedes` | да | воркер, аудит |
| Доступ | `access_group`, `visibility: public\|internal` | да | фильтр видимости |
| Класс и политика | `class: pure\|corp-read\|side-effect`, `execution: sandbox\|worker` | да | драйвер исполнения, CI-линт |
| Контракт I/O | `io.input`, `io.output` (JSON Schema, `additionalProperties: false`), `io.units`, `io.locale`, `io.format`, `io.errors` | да (`errors` — нет) | валидация графа, песочница, tool-schema |
| Исполнение | `entrypoint`, `runtime.image@sha256`, `runtime.deps` (lock с хешами), `runtime.limits` (cpu/mem/pids/timeout_s) | да | драйвер песочниц, воркер |
| Блок для модели (слой B) | `llm.name`, `llm.description`, `llm.when_to_use`, `llm.when_not_to_use`, `llm.examples` | да | ИИшка |
| Качество | `tests.golden` (эталонные пары вход→выход), `tests.selection` (≥10 запросов), `tests.eval_model: local-default` | да | CI-гейт |
| Наблюдаемость | `audit.log_inputs: hash\|full`, `trace_tags` | да | Langfuse, аудит |

Правила, вытекающие механически:
* `execution: sandbox` ⇒ `class: pure` (в песочнице `--network none`).
* `class: corp-read` ⇒ I/O выполняет воркер по mTLS (аудит доступа к корп. данным), вычисление — в песочнице с данными на входе.
* `class: side-effect` ⇒ только воркер; выше по графу есть HITL; объявлена идемпотентность.
* `visibility: internal` ⇒ не публикуется в общем списке.
* Блок `llm` без примеров ≤ 512 токенов (прогрессивное раскрытие); полный манифест читается только после выбора.
* Имя `llm.name` стабильно между версиями; изменение поведения — новая мажорная версия, новое имя (`supersedes`).

Пример:

```yaml
id: finance.invoice.totals
version: 1.3.0
kind: algorithm
owner: andrei-shaban
lifecycle: active
access_group: fab-finance
visibility: public

class: pure
execution: sandbox

io:
  input: schemas/totals.in.json
  output: schemas/totals.out.json
  units: {money: RUB, precision: 2, rounding: half-up}
  locale: ru-RU
  format: {date: ISO-8601, number: "#,##0.00"}

entrypoint: totals:compute
runtime:
  image: toolset-finance@sha256:…
  deps: requirements.lock
  limits: {cpu: 1, mem: 512Mi, pids: 64, timeout_s: 30}

llm:
  name: compute_invoice_totals
  description: >
    Считает итоги счёта (НДС, скидки, округления по правилам РФ)
    по извлечённым позициям. Возвращает итог и детализацию.
  when_to_use: после извлечения позиций, перед diff-формой согласования
  when_not_to_use: черновики без позиций; пересчёт уже утверждённых итогов
  examples: [golden/case-01.json, golden/case-02.json, golden/negative-01.json]

tests:
  golden: golden/
  selection: selection/queries.jsonl
  eval_model: local-default

audit:
  log_inputs: hash
trace_tags: [finance, invoice]
```

#### 3.7.4. Манифест сценария — состав

| Блок | Поля | Обяз. | Кто читает |
| --- | --- | --- | --- |
| Идентичность | `id`, `version`, `kind: scenario`, `owner`, `lifecycle` | да | воркер, аудит |
| Доступ | `access_group` | да | фильтр видимости |
| Семантика (слой B) | `description`, `when_to_use`, `when_not_to_use`, `examples` | да | ИИшка, ассемблер, роутер |
| Запуск | `trigger.mode: operator\|event\|schedule\|router`; для router — `allowed_set`, `classifier_schema` | да | Gateway |
| Граф | `graph: graph.py:build`, `state` (JSON Schema) | да | воркер, сверка с графом |
| Композиция | `nodes`: `id`, `type: tool\|llm\|algorithm\|hitl\|router`, `ref@version`, для llm — `output`, для hitl — `form` + `resume`; `edges`: `from`, `to`, `if` | да | резолв версий, сверка с графом |
| Требования | `requires.gpu`, `requires.corp`, `requires.tools` | да | планировщик контуров |
| SLA | `hitl_horizon_days` (→ TTL Streams), `max_run_minutes`, `max_parallel_runs` | да | Redis TTL, лимиты |
| Политика | `side_effect_requires_hitl`, `side_effect_requires_idempotency` | да | CI-линт |
| Наблюдаемость | `audit.points`, `trace_tags` | да | Langfuse, аудит |
| ROI | `rollout.pilot_metrics` | да | пилот, отчёт |

Правила композиции:
* `nodes` + `edges` декларируют порядок и условия ветвления; условие `if` — детерминированный предикат над состоянием, вычисляется рантаймом графа, не моделью.
* Код графа обязан реализовать ровно объявленные рёбра; ветка в коде без объявления в манифесте и наоборот — ошибка регистрации.
* Узлы с `class: side-effect` достижимы только через ноду `hitl` (CI-линт).

Пример:

```yaml
id: invoice-processing
version: 2.1.0
kind: scenario
owner: andrei-shaban
lifecycle: active
access_group: fab-accounting

description: Обработка входящего счёта до проведения в учётной системе.
when_to_use: поток входящих счетов в PDF/сканах; от извлечения до проводки
when_not_to_use: договоры, служебные записки, корректировочные счета
examples: [examples/req-01.txt, examples/req-02.txt, examples/req-negative-01.txt]

trigger:
  mode: operator

graph: graph.py:build
state: schemas/state.json

composition:
  nodes:
    - {id: ocr,     type: tool,      ref: ocr.paddle.batch@1.2.0}
    - {id: extract, type: llm,       output: schemas/extract.json}
    - {id: totals,  type: algorithm, ref: finance.invoice.totals@1.3.0}
    - {id: approve, type: hitl,      form: a2ui/diff, resume: schemas/approval.json}
    - {id: post,    type: algorithm, ref: arm.create_document@2.0.0}   # side-effect
    - {id: reject,  type: tool,      ref: notify.operator@1.0.0}
  edges:
    - {from: ocr,     to: extract}
    - {from: extract, to: totals}
    - {from: totals,  to: approve}
    - {from: approve, to: post,   if: state.approved == true}
    - {from: approve, to: reject, if: state.approved == false}

requires:
  gpu: [llm, ocr, embeddings]
  corp: [vm4.read, arm.write]
  tools: [ocr.paddle.batch]

sla:
  hitl_horizon_days: 30
  max_run_minutes: 60
  max_parallel_runs: 8

policy_lint:
  side_effect_requires_hitl: true
  side_effect_requires_idempotency: true

audit:
  points: [hitl, corp-access]
trace_tags: [invoice, accounting]

rollout:
  pilot_metrics: [time_per_doc, error_rate]
```

#### 3.7.5. Требования к блоку для модели (нормативные)

Цель блока — модель однозначно понимает, ЧТО, КОГДА и ГДЕ применять. Требования обязательны для регистрации манифеста.

Для алгоритма (`llm`-блок):
1. `name`: глагол_существительное, уникальный, единый стиль; стабилен между версиями.
2. `description`: 1–3 предложения; что делает, на каких данных, какой результат. Без деталей реализации.
3. `when_to_use`: перечень триггерных ситуаций в терминах процесса.
4. `when_not_to_use`: минимум один пункт; при наличии похожих инструментов — обязательное разграничение.
5. Вход: поле — тип + описание + единицы/формат (валюта, точность, округление, даты, локаль); ограниченные значения — только `enum`.
6. Выход: схема + описание, как интерпретировать результат.
7. Класс дополняется аннотациями в формате MCP: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` (вычисляются из `class`, не дублируются вручную).
8. `examples`: ≥2 эталонные пары вход→выход; ≥1 контрпример к `when_not_to_use`.
9. Лимит: метаданные блока (без примеров) ≤ 512 токенов — полный манифест читается только после выбора.
10. Изменение поведения без смены имени и мажорной версии запрещено; устаревание — через `supersedes`.

Для сценария (блок выбора):
1. `description` — бизнес-задача, а не технический состав.
2. `when_to_use` — триггерные ситуации и признаки входных данных.
3. `when_not_to_use` — границы применимости, обязательны.
4. Примеры: 2–3 типовые формулировки запросов + 1–2 неподходящие.
5. Требования и разрешения — в человекочитаемых терминах.
6. Тот же токен-лимит; полный манифест — только после выбора.

#### 3.7.6. Правила выбора

* Рантайм: модель видит только инструменты, привязанные к текущей ноде; подача всего набора манифестов в рантайм-контекст запрещена. Видимость при выборе = `группы пользователя ∩ access_group`.
* На одну ноду — не более 12 инструментов; при превышении — группировка и роутинг до подачи в контекст.
* Ассемблер фабрики (design-time, при появлении потребности): поиск по манифестам с тем же предикатом групп → чтение полных манифестов кандидатов → человек утверждает.
* Роутер в проде выбирает только из объявленного в сценарии `allowed_set`.

#### 3.7.7. Оценка и CI-гейты

* Регистрация манифеста невозможна без: проходящих эталонных тестов алгоритма, заполнения блока для модели по §3.7.5, пройденного policy-линта (класс → исполнение, песочница ⇒ только `pure`, перед `side-effect` есть HITL, объявлена идемпотентность, рёбра манифеста совпадают с графом).
* Набор эталонов выбора (`tests.selection`): ≥10 запросов на сценарий и инструмент (подходящие и неподходящие); точность выбора моделью ≥95% — обязательное условие регистрации.
* Модель оценки фиксируется в манифесте: `tests.eval_model: local-default`; при замене модели на инференс-узле — обязательный повтор всех наборов эталонов выбора (пункт Runbook).
* Линт дублей: высокая попарная близость описаний требует явного разграничения в `when_not_to_use`.

## 4. Межсерверные маршруты

| Направление | Порт | Назначение |
| --- | --- | --- |
| Браузер → ВМ №1 | 443 | единственный вход (SPA, индекс `scenarios.json`, UI Langfuse) |
| ВМ №1 → LDAP/AD | 636 | Keycloak LDAP federation |
| ВМ №1 → ВМ №2 | 8333 | S3 TLS: файлы, Langfuse blob |
| ВМ №2 → ВМ №1 | 8333 | S3 TLS: репликация бэкапов PG/WAL на off-host инстанс |
| ВМ №1 (Gateway) → ВМ №2 (PostgreSQL) | 5432 | TLS + `scram-sha-256`: роль только реестра ранов (чтение/запись статусов) |
| ВМ №1 (Gateway) → ВМ №2 (Redis фабрики) | 6379 | TLS + ACL `agui_svc`: постановка задач, `XREAD` событий, реконнект |
| ВМ №2 → ВМ №1 (зеркала) | 443 | Docker registry, PyPI, npm через nginx, internal CA: pull образов, wheels, пакетов |
| GPU (узел №3) → ВМ №1 (registry) | 443 | pull образов, internal CA |
| ВМ №2 (Worker) → ВМ №2 (PostgreSQL) | 5432 | локально: чекпоинты LangGraph, реестр ранов, векторный поиск RAG |
| ВМ №2 (Worker) → ВМ №2 (SeaweedFS) | 8333 | внутренний S3 TLS: артефакты агентов, Diff-файлы, бэкапы БД |
| ВМ №2 (Worker) → ВМ №1 (Langfuse) | 443 | OTel-инжест: отдельный `server_name`, mTLS клиентским сертификатом воркера |
| ВМ №2 (Worker) → ВМ №4 (Корп. PG) | 5432 | mTLS: чтение мастер-данных, реестров, справочников (read-only) |
| ВМ №2 → GPU ЕНДПОИНТЫ | 443 | mTLS: LLM `/`, embeddings, OCR `/ocr/` |
| ВМ №2 → рабочая станция | 8443 | mTLS-интеграция: выполнение бизнес-операций в корпоративных системах |
| ВМ №1 → GPU ЕНДПОИНТЫ | 443 | опционально: metrics/health, отдельный client cert |
| ВМ №1, ВМ №2, GPU, ВМ №4 → NTP | 123 | синхронизация времени |

> **Примечания:** Redis Langfuse и PostgreSQL (Auth & Observability) доступны только контейнерам внутри ВМ №1 и межсерверных маршрутов не требуют. Манифесты доставляются на ВМ №2 как артефакты и читаются воркером через bind-mount; сетевого маршрута для них нет. Песочницы не имеют сетевых маршрутов никуда: зависимости и данные доставляются воркером через локальные тома. Рабочая станция — внешний корпоративный контур: АРМ оператора; при интеграции через шлюз во внутреннюю сеть доступ осуществляется только через mTLS с ВМ №2.

## 6. Радар технологий и политика внедрения (Technology Radar & Adoption Policy)

Раздел фиксирует решения по внешним отраслевым стандартам: что входит в базовый стек, что допускается как опциональное расширение и что находится в наблюдении. Базовый стек (§2) не меняется без отдельного утверждённого решения.

### 6.1. Политика внедрения
* Новый компонент и протокол внедряется только при измеримой выгоде для сценариев заказчика, совместимости с Air-Gap и отсутствии vendor lock-in.
* Приоритет — стандартам под нейтральным управлением (Linux Foundation, AAIF) в статусе GA.
* Статусы: **IN STACK** (базовый стек, §2), **OPTIONAL** (по требованию, с условиями активации), **WATCH** (наблюдение, не внедрять).
* Пересмотр WATCH — при старте нового проекта и раз в квартал; изменение статуса фиксируется отдельным утверждённым решением.

### 6.2. MCP — опциональный адаптер по требованию (OPTIONAL)

**Статус:** OPTIONAL, в базовый стек не входит. Инструменты платформы остаются детерминированными Python-библиотеками в песочницах (§3.2).

**Основание:** ревизия MCP `2026-07-28` (stateless-ядро, Multi Round-Trip Requests, header-based routing) пригодна как внутренний HTTP-транспорт инструментов в изолированном контуре; MCP — стандарт AAIF/Linux Foundation (https://modelcontextprotocol.io/specification/2026-07-28).

**Триггеры активации (любой из):**
1. У заказчика появились корпоративные MCP-серверы, необходимые в сценариях.
2. Возникла потребность переиспользовать инструменты между фабриками и инсталляциями.

**Архитектурные ограничения при активации:**
* Тонкий MCP-клиент исполняется в воркере (единый Python-образ, §3.6); Gateway, графы, реестр ранов и песочницы не изменяются.
* MCP-серверы — только во внутреннем контуре: ВМ №2 (внутренняя сеть контейнеров), доступ воркеру через mTLS по правилам §3.2; маршрут добавляется в матрицу §4 только при активации.
* Песочницы не получают сетевого доступа к MCP-серверам; все вызовы идут через воркер.
* MCP-инструменты с побочными эффектами проходят HITL и идемпотентность наравне с бизнес-операциями АРМ (§5.6).
* Доступ к MCP-серверам логируется и трейсится в Langfuse как доступ к корпоративным данным (§5.7).
* Air-Gap: образы MCP-серверов по digest из внутреннего зеркала, телеметрия отключена, секреты не попадают в песочницы и трейсы.
* Пин ревизии протокола — `2026-07-28`; SDK и версии компонентов фиксируются отдельным решением при активации.

**DoD адаптера (применяется только при активации):**
- [ ] MCP-клиент в воркере: stateless HTTP, таймауты и ретраи, без сессионного состояния.
- [ ] Маршрут до MCP-сервера внесён в §4 и применён на межсетевом экране; лишнего egress нет.
- [ ] Вызов MCP-инструмента виден в Langfuse: trace_id, кто, когда, что.
- [ ] Инструмент с побочным эффектом: двойной вызов → ровно один эффект.
- [ ] Песочница не имеет маршрута к MCP-серверу (проверено).
