# БЛУПРИНТ МЕТА-СЦЕНАРИЯ
## Архитектор сценариев (Scenario Architect)

**Версия документа:** 1.0.0  
**Статус:** утверждён как единственный источник истины для реализации  
**Связь с SSOT:** Production Blueprint v5.2.1 — все ограничения наследуются без исключений  
**Автор:** Andrei Shaban

---

## 1. Зачем нужен этот сценарий

### 1.1. Проблема, которую он решает

Платформа «Фабрика агентов и алгоритмов» предметно-независима (§1, Executive Summary). Это значит, что для каждого нового заказчика или нового бизнес-процесса нужно:

- описать новый сценарий;
- подобрать или создать алгоритмы;
- написать код графа;
- определить схемы;
- написать тесты;
- зарегистрировать манифест;
- проверить политику;
- упаковать для каталога.

Сегодня это делает разработчик вручную. Каждый раз. С нуля. Зная конвенции §3.7.3–§3.7.7 наизусть.

Это узкое горлышко масштабирования платформы.

### 1.2. Что меняет Архитектор

Архитектор сценариев превращает процесс создания нового сценария из ручной разработки в **управляемый конвейер с человеческим контролем**:

> Пользователь описывает бизнес-задачу → Архитектор проектирует решение → детерминированные алгоритмы проверяют → человек утверждает → платформа получает готовый пакет для размещения в каталоге.

Это не «ИИ пишет код за программиста». Это **инструмент снижения порога входа** при сохранении всех гарантий безопасности, изоляции и аудита.

### 1.3. Позиционирование в продуктовой линейке

Архитектор — это **мета-сценарий**. Он не автоматизирует бизнес-процесс заказчика. Он автоматизирует процесс создания автоматизации.

Это значит:

- его пользователь — не конечный бизнес-оператор, а **внедренец, архитектор или power user**;
- его выход — не бизнес-результат, а **артефакт для каталога фабрики**;
- его качество измеряется не «сколько счетов обработано», а «сколько времени сэкономлено на создании нового сценария».

## 2. Название и идентичность

### 2.1. Почему именно «Архитектор сценариев»

Рассматривались варианты:

| Вариант | Почему отклонён |
|---|---|
| Фабричный архитектор | Слишком широко: звучит как инструмент проектирования всей платформы, включая инфраструктуру, доступы, GPU-кластер |
| Конструктор сценариев | Звучит как low-code wizard для нетехнических пользователей; не отражает глубину проверок и безопасности |
| Blueprint Architect | Англоязычное; не совпадает с русским интерфейсом и тоном личного бренда |
| Scenario Forge | Маркетинговое название, не несёт архитектурного смысла |

**Архитектор сценариев** — точное, понятное, масштабируемое название. Если позже потребуется расширить до проектирования алгоритмов и инструментов отдельно, можно будет ввести `factory.algorithm.architect` без переименования.

### 2.2. Идентификатор

```
ID:          factory.scenario.architect
Kind:        scenario
Version:     0.1.0 (до первого production-прогона)
Owner:       andrei-shaban
Lifecycle:   active
Access:      fab-architect
```

### 2.3. Конвенция версионирования

- `0.1.0` — внутренняя разработка, тесты на стенде.
- `1.0.0` — первый успешный цикл «запрос → утверждение → пакет размещён в staging».
- Далее — semver по §3.7.3: мажорная при изменении контракта, минорная при расширении.
- Пара `(id, version)` immutable. Изменение — только новой версией.

## 3. Границы ответственности

### 3.1. Что Архитектор делает

| # | Действие | Результат |
|---|---|---|
| 1 | Проводит структурированное интервью с пользователем | Нормализованный бриф задачи |
| 2 | Определяет предметную область и границы сценария | Список процессов, данных, ролей |
| 3 | Инвентаризирует существующие активы фабрики | Карта переиспользования |
| 4 | Проектирует граф, манифест, схемы | Утверждённый дизайн |
| 5 | Генерирует код графа на LangGraph | `graph.py` + вспомогательные модули |
| 6 | Генерирует тесты | Golden, selection, unit |
| 7 | Генерирует документацию | README, CHANGELOG, examples |
| 8 | Проверяет пакет детерминированными валидаторами | Отчёт о прохождении/отказе |
| 9 | Запускает тесты в песочнице | Протокол исполнения |
| 10 | Собирает каталожную обёртку | `bundle.json`, `provenance.json`, checksums |
| 11 | Предоставляет HITL-точки для утверждения | Лог решений человека |

### 3.2. Что Архитектор НЕ делает и почему

| Запрет | Обоснование |
|---|---|
| Не пишет напрямую в production-каталог | §1: «Принцип автономности артефактов» — размещение через отдельный процесс с аудитом |
| Не обращается к корпоративным данным (ВМ №4) | §3.2: доступ к корп. данным — только через mTLS воркера с аудитом; Архитектор не имеет бизнес-контекста заказчика |
| Не выполняет side-effect операции | §3.7.4: `side-effect` только через воркера + HITL + идемпотентность |
| Не изменяет существующие манифесты | §3.7.1: пара `(id, version)` immutable |
| Не использует внешние сети | §1: Air-Gap, полная автономность |
| Не хранит секреты в генерируемом коде | §3.2: секреты не передаются в песочницы |
| Не обходит CI-гейты | §5.5: регистрация невозможна без тестов, полиси-линта, сверки графа |
| Не внедряет MCP / A2A / WebMCP / Agent Skills | §6: статус WATCH, не внедрять |
| Не принимает решение о доступе | §3.7.2: доступ применён до модели, модель не решает |

### 3.3. Антипаттерны, которые Архитектор предотвращает

| Антипаттерн | Как предотвращается |
|---|---|
| Сценарий без `when_not_to_use` | Policy-lint блокирует регистрацию |
| Все алгоритмы в одном графе без переиспользования | Архитектор принудительно ищет существующие активы |
| Модель видит весь каталог | `discover_allowed_assets` строит allowlist до контекста |
| Побочный эффект без HITL | Граф не генерируется без ноды `hitl` перед `side-effect` |
| Тесты написаны «на глаз» | Генерируются структурированные golden/selection наборы с порогами |
| Версии «возьмём последнюю» | Манифест требует точных `ref@version` |
| Код без форматирования | Генерация следует фиксированному style guide; линтер проверяет |

## 4. Пользовательский путь (пошагово)

### 4.1. Этап 1: Входной запрос

Пользователь приходит с неструктурированным описанием:

> «Мне нужен сценарий обработки входящих договоров: загрузить файл, распознать, извлечь реквизиты, сравнить с шаблоном, показать отличия менеджеру, после подтверждения создать черновик в учётной системе.»

Архитектор **не начинает генерировать код**. Он начинает **интервью**.

### 4.2. Этап 2: Структурированное интервью

Архитектор задаёт вопросы по фиксированному чек-листу:

**Бизнес-контекст:**
- Какая задача решается?
- Кто инициирует процесс?
- Кто утверждает результат?
- Какой объём операций в день/неделю?
- Какие системы затронуты?

**Данные:**
- Какие входные данные (формат, источник)?
- Какие выходные данные (формат, потребитель)?
- Есть ли мастер-данные, справочники?
- Нужен ли доступ к корпоративным реестрам?

**Управление:**
- Нужны ли точки человеческого контроля?
- Какие решения принимает человек?
- Какой горизонт паузы (дни, недели)?
- Что происходит при отказе?

**Безопасность и доступ:**
- Кто имеет право запускать сценарий?
- Какие группы доступа?
- Есть ли чувствительные данные?

**Интеграции:**
- Какие внешние системы?
- Какой протокол (mTLS, API, файл)?
- Есть ли идемпотентность на стороне целевой системы?

Результат этапа: **нормализованный бриф** — структурированный JSON, соответствующий схеме `schemas/brief.json`.

### 4.3. Этап 3: Инвентаризация активов

Архитектор вызывает детерминированный алгоритм `architect.discover_allowed_assets`:

1. Читает in-memory индекс манифестов (§3.7.1).
2. Фильтрует по `группы пользователя ∩ access_group` (§3.7.2).
3. Возвращает **только разрешённые** активы.

Важно: модель **никогда не видит** манифесты, к которым у пользователя нет доступа. Это не фильтрация вывода — это фильтрация входа.

Результат:

```json
{
  "available_algorithms": [
    {"id": "finance.invoice.totals", "version": "1.3.0", "class": "pure"},
    {"id": "ocr.paddle.batch", "version": "1.2.0", "class": "pure"}
  ],
  "available_tools": [
    {"id": "notify.operator", "version": "1.0.0"}
  ],
  "missing_capabilities": [
    "Распознавание договоров (нет существующего алгоритма)"
  ]
}
```

### 4.4. Этап 4: Проектирование

Архитектор генерирует **черновик дизайна**:

- Список узлов графа (тип, ref, назначение).
- Рёбра и условия ветвления.
- Точки HITL.
- Схемы состояния.
- Требования к GPU, корпоративным данным, инструментам.
- Группа доступа.
- `when_to_use` / `when_not_to_use`.

**Дизайн проверяется детерминированным линтером** (`architect.policy_lint_design`):

| Проверка | Правило из SSOT |
|---|---|
| Песочница ⇒ только `pure` | §3.7.3 |
| `corp-read` ⇒ воркер + mTLS + аудит | §3.7.3 |
| `side-effect` ⇒ HITL выше по графу | §3.7.4 |
| `side-effect` ⇒ идемпотентность | §3.7.4 |
| `interrupt()` в отдельной ноде | §3.1 |
| Блок для модели ≤ 512 токенов | §3.7.5 |
| Все `ref` — точные версии | §3.7.1 |
| Рёбра манифеста = рёбра графа | §3.7.4 |

### 4.5. Этап 5: Утверждение дизайна (HITL #1)

Пользователь видит:

- Визуализацию графа (узлы, рёбра, условия).
- Манифест в YAML.
- Список переиспользованных активов.
- Список новых компонентов.
- Предупреждения линтера.
- Кнопки: **Утвердить / Доработать / Отклонить**.

Без утверждения генерация кода **не начинается**.

### 4.6. Этап 6: Генерация пакета

После утверждения Архитектор генерирует:

```
<scenario-id>/<version>/
  manifest.yaml          ← канон, источник истины
  graph.py               ← исполнимая реализация на LangGraph
  schemas/
    input.json           ← схема входа
    state.json           ← схема состояния графа
    output.json          ← схема выхода
    errors.json          ← схема ошибок
  nodes/                 ← вспомогательные модули (если нужны)
  tests/
    golden/              ← эталонные пары вход→выход
    selection/           ← запросы для проверки выбора (≥10)
    unit/                ← модульные тесты
  examples/              ← примеры запросов
  README.md              ← описание, инструкция, ограничения
  CHANGELOG.md           ← история версий
  bundle.json            ← каталожная обёртка
  provenance.json        ← кто, когда, какая модель, какой шаблон
  checksums.txt          ← SHA-256 всех файлов
  license.spdx           ← лицензия (наследуется от платформы)
  notice.txt             ← атрибуция
```

### 4.7. Этап 7: Валидация и тестирование

Сгенерированный пакет проходит конвейер проверок:

```
Статический анализ (AST)
  → Запрещённые импорты?
  → Хардкод секретов?
  → Сетевые вызовы?
  → Динамический exec/eval?
  
Валидация манифеста
  → Схема §3.7.4 корректна?
  → Все обязательные поля заполнены?
  → Семантика не пустая?
  
Сверка манифест ↔ граф
  → Узлы совпадают?
  → Рёбра совпадают?
  → Предикаты валидны?
  
Запуск в песочнице (gVisor)
  → runsc, --network none, read-only rootfs
  → Golden tests passed?
  → Unit tests passed?
  → Selection tests accuracy ≥ 95%?
  
Policy-lint
  → Все правила §3.7.3–§3.7.7 соблюдены?
```

Если проверки не пройдены — Архитектор **возвращается к генерации** с указанием конкретных ошибок. Максимум 3 итерации. После — эскалация человеку.

### 4.8. Этап 8: Утверждение пакета (HITL #2)

Пользователь видит:

- Diff всех файлов.
- Результаты тестов.
- Предупреждения.
- Digest пакета.
- Предполагаемое место в каталоге.
- Кнопки: **Принять / Доработать / Отклонить**.

### 4.9. Этап 9: Финализация

Если пакет принят:

1. Формируется `bundle.json` с полными метаданными.
2. Считаются digest всех файлов.
3. Записывается `provenance.json`.
4. Готовится patch для `scenarios.json`.
5. Пакет передаётся в staging-каталог (через `architect.artifact_emitter`).

**В MVP запись в production-каталог не выполняется.** Только формирование артефакта.

## 5. Архитектура самого Архитектора

### 5.1. Граф сценария

```
intake
  → clarify
  → normalize_brief          [algorithm, pure]
  → discover_allowed_assets  [algorithm, corp-read → worker]
  → draft_design             [llm]
  → lint_design              [algorithm, pure]
  → approve_design           [hitl, form: a2ui/design_review]
  → generate_code            [llm]
  → scaffold_files           [tool, sandbox]
  → run_sandbox_tests        [algorithm, worker]
  → review_package           [hitl, form: a2ui/package_diff]
  → finalize_bundle          [algorithm, pure]
  → emit_artifact            [tool, worker]
```

### 5.2. Ветвления и возвраты

```
approve_design:
  approved == true  → generate_code
  approved == false → draft_design (retry_count < 3)
  approved == false → END (retry_count >= 3)

run_sandbox_tests:
  tests_passed == true  → review_package
  tests_passed == false → generate_code (fix_attempts < 3)
  tests_passed == false → END (fix_attempts >= 3)

review_package:
  package_approved == true  → finalize_bundle
  package_approved == false && redesign → draft_design
  package_approved == false && abort → END
```

**Все циклы ограничены.** Нет бесконечных петель. После 3 попыток — остановка с полным логом и объяснением.

### 5.3. Типы узлов

| Узел | Тип | Исполнение | Обоснование |
|---|---|---|---|
| `intake` | llm | worker | Понимание естественного языка |
| `clarify` | llm | worker | Уточняющие вопросы |
| `normalize_brief` | algorithm | sandbox | Детерминированная валидация брифа |
| `discover_allowed_assets` | algorithm | worker | Требует доступа к индексу манифестов (§3.7.1) |
| `draft_design` | llm | worker | Генерация архитектуры |
| `lint_design` | algorithm | sandbox | Детерминированные проверки |
| `approve_design` | hitl | — | Человек утверждает дизайн |
| `generate_code` | llm | worker | Генерация кода |
| `scaffold_files` | tool | sandbox | Запись файлов во временный том |
| `run_sandbox_tests` | algorithm | worker | Оркестрация тестов в gVisor |
| `review_package` | hitl | — | Человек утверждает пакет |
| `finalize_bundle` | algorithm | sandbox | Digest, bundle, provenance |
| `emit_artifact` | tool | worker | Копирование в staging-каталог |

### 5.4. Почему `normalize_brief` и `lint_design` в песочнице, а `discover_allowed_assets` на воркере

- **Песочница** (`runsc`, `--network none`): для чистых вычислений без доступа к данным платформы. Бриф и дизайн — это данные, которые не требуют чтения индекса манифестов.

- **Воркер**: для `discover_allowed_assets`, потому что нужен доступ к in-memory индексу манифестов (§3.7.1), который живёт в памяти воркера. Песочница не имеет сетевого доступа и не видит индекс.

- **Воркер**: для `run_sandbox_tests`, потому что оркестрация контейнеров песочницы — это привилегированная операция через Docker socket proxy (§3.2).

## 6. Детализация ключевых алгоритмов

### 6.1. `architect.normalize_brief`

**Назначение:** превратить свободный текст пользователя в структурированный бриф.

**Вход:**
```json
{
  "raw_text": "string, описание задачи от пользователя",
  "interview_answers": {"business_goal": "...", "inputs": "...", "outputs": "..."}
}
```

**Выход:**
```json
{
  "business_goal": "string",
  "domain": "string",
  "input_format": {"type": "pdf|image|text|structured", "source": "string"},
  "output_format": {"type": "document|record|report|notification", "target": "string"},
  "hitl_points": [{"action": "string", "role": "string"}],
  "systems": [{"name": "string", "protocol": "mtls|api|file", "direction": "read|write"}],
  "access_group": "string",
  "volume": {"per_day": "integer", "per_week": "integer"},
  "sla_requirements": {"max_duration_minutes": "integer", "hitl_horizon_days": "integer"}
}
```

**Ограничения:**
- `class: pure` — не читает внешние данные.
- `execution: sandbox` — изолированный запуск.
- Валидация через JSON Schema с `additionalProperties: false`.

### 6.2. `architect.discover_allowed_assets`

**Назначение:** найти переиспользуемые активы, доступные текущему пользователю.

**Критическое требование (§3.7.2):**

> Модель не принимает решение о доступе: доступ применён до неё.

Алгоритм выполняется **на воркере**, потому что:
1. Читает in-memory индекс манифестов (§3.7.1).
2. Знает группы пользователя из principal-контекста.
3. Возвращает только пересечение `группы пользователя ∩ access_group`.

**Вход:**
```json
{
  "user_groups": ["fab-architect", "fab-finance"],
  "required_capabilities": ["ocr", "totals_calculation", "document_creation"],
  "exclude_ids": ["deprecated.algorithm@0.9.0"]
}
```

**Выход:**
```json
{
  "available_algorithms": [...],
  "available_tools": [...],
  "missing_capabilities": ["..."],
  "total_visible": 12,
  "total_filtered_out": 37
}
```

**Аудит:** фиксируется, сколько манифестов было скрыто от модели. Это метрика безопасности.

### 6.3. `architect.policy_lint_design`

**Назначение:** проверить черновик дизайна до утверждения человеком.

**Проверяет:**

| Правило | Источник в SSOT |
|---|---|
| `execution: sandbox` ⇒ `class: pure` | §3.7.3 |
| `class: corp-read` ⇒ воркер + mTLS | §3.7.3 |
| `class: side-effect` ⇒ HITL выше по графу | §3.7.4 |
| `class: side-effect` ⇒ идемпотентность объявлена | §3.7.4 |
| `interrupt()` в отдельной ноде | §3.1 |
| Блок для модели ≤ 512 токенов | §3.7.5 |
| Все `ref` — точные версии, не «последняя» | §3.7.1 |
| Рёбра манифеста ⊆ рёбра графа и наоборот | §3.7.4 |
| `when_not_to_use` не пустой | §3.7.5 |
| `examples` ≥ 2 положительных + ≥ 1 отрицательный | §3.7.5 |
| `access_group` указан | §3.7.4 |
| `hitl_horizon_days` ≤ 30 (TTL Streams) | §3.1 |

**Выход:**
```json
{
  "passed": false,
  "errors": [
    {"rule": "side_effect_requires_hitl", "node": "post_document", "message": "Узел 'post_document' (side-effect) не имеет HITL выше по графу"}
  ],
  "warnings": [
    {"rule": "token_limit", "block": "llm", "tokens": 547, "message": "Блок для модели превышает 512 токенов"}
  ],
  "suggestions": [...]
}
```

### 6.4. `architect.sandbox_validator`

**Назначение:** запустить сгенерированные тесты в изолированной среде.

**Как работает:**
1. Получает структуру файлов пакета.
2. Монтирует их в контейнер песочницы.
3. Запускает `runsc` с параметрами:
   - `--network none`
   - `--read-only`
   - `--tmpfs /tmp`
   - `--cap-drop ALL`
   - `--no-new-privileges`
   - `--memory 512m`
   - `--pids-limit 64`
   - `--timeout 60s`
4. Исполняет тесты.
5. Парсит результаты.

**Что проверяется:**
- Импорт модулей без ошибок.
- Golden tests: вход → ожидаемый выход.
- Unit tests: логика, ветвления, обработка ошибок.
- Отсутствие сетевых вызовов (проверяется на уровне ядра, не кода).
- Отсутствие доступа к файловой системе за пределами `/tmp`.

**Результат:**
```json
{
  "all_passed": false,
  "golden": {"total": 5, "passed": 4, "failed": 1},
  "unit": {"total": 12, "passed": 12, "failed": 0},
  "selection": {"accuracy": 0.92, "threshold": 0.95, "passed": false},
  "security": {"violations": []},
  "errors": [
    {"test": "golden/case-03", "expected": "...", "got": "...", "traceback": "..."}
  ]
}
```

## 7. Взаимодействие с UI

### 7.1. Протокол

Все формы рендерятся через **AG-UI** (§3.5) + **A2UI toolkit** (`ag-ui-a2ui-toolkit==0.0.6`). Фронтенд — `@assistant-ui/react-ag-ui` поверх `HttpAgent` (`@ag-ui/client` ≥ 1.0.3).

Никаких vendor-рантаймов. Никаких CopilotKit. Статика через nginx.

### 7.2. Форма утверждения дизайна

**Когда показывается:** после `lint_design`, перед генерацией кода.

**Что содержит:**
- Визуализация графа (узлы, рёбра, условия).
- Манифест в YAML с подсветкой.
- Список переиспользованных активов.
- Список новых компонентов.
- Предупреждения и ошибки линтера.
- Кнопки: Утвердить / Доработать / Отклонить.
- Поле для комментариев.

**Что фиксируется в аудите:**
- Кто утвердил.
- Когда.
- Какие изменения внёс (если доработал).
- Версию дизайна до и после.

### 7.3. Форма утверждения пакета

**Когда показывается:** после `run_sandbox_tests`, перед финализацией.

**Что содержит:**
- Список файлов с размерами и digest.
- Diff по каждому файлу (если есть предыдущая версия).
- Результаты тестов (таблица: тип, всего, прошло, упало).
- Предупреждения безопасности.
- Кнопки: Принять / Доработать / Отклонить.

### 7.4. Особенности

- Формы **модальные в потоке диалога**, не отдельные страницы.
- Поддержка `Last-Event-ID` для реконнекта (§3.4).
- Если пользователь закрыл вкладку — ран не теряется, состояние в PostgreSQL чекпоинтах (§3.1).
- Двойное утверждение → ровно один эффект (idempotency-key, §3.1).

## 8. Безопасность генерируемого кода

### 8.1. Статический анализ (до запуска)

Перед тем как код попадёт в песочницу, он проходит AST-анализ:

**Запрещено:**
```python
# Сеть
import socket, http.client, urllib, requests, httpx, aiohttp

# Файловая система за пределами /tmp
open('/etc/...'), open('/root/...'), open('/home/...')

# Секреты
os.environ['SECRET'], os.getenv('TOKEN')

# Динамический код
eval(), exec(), compile(), __import__()

# Подпроцессы
subprocess, os.system, os.popen

# Сериализация с кодом
pickle, marshal, shelve
```

### 8.2. Изоляция исполнения

Весь сгенерированный код исполняется в песочнице с параметрами §3.2:

- `runsc` (gVisor) — пользовательский уровень ядра.
- `--network none` — нет сети вообще.
- `--read-only` — корневая ФС только для чтения.
- `--tmpfs /tmp` — временные данные в памяти.
- `--cap-drop ALL` — без привилегий.
- `--no-new-privileges` — без эскалации.
- Лимиты: CPU, память, PID, таймаут.

### 8.3. Зависимости

Сгенерированный код не может устанавливать пакеты из интернета.

Допустимые зависимости:
- Только из внутреннего зеркала PyPI (§3.2).
- Только через предзапечённый wheel-cache.
- `pip install --no-index --find-links /cache --require-hashes`.
- Состав кэша фиксируется хешами.

### 8.4. Запрет на секреты

В генерируемом коде **не должно быть**:
- Токенов.
- Паролей.
- Приватных ключей.
- Путей к сертификатам.
- Адресов внутренних сервисов.

Все секреты доставляются через механизмы платформы (secrets manager, bind-mount), а не вшиваются в код.

## 9. Соответствие OpenSSF Best Practices

| Требование OpenSSF | Как выполняется в Архитекторе |
|---|---|
| Управление зависимостями | `requirements.lock` с хешами, `--require-hashes` |
| Supply chain security | `provenance.json`, `checksums.txt`, digest всех файлов |
| Изоляция исполнения | gVisor, `--network none`, rootless |
| Криптографическая защита | mTLS для всех интеграций, SHA-256 для digest |
| Наблюдаемость | Все шаги в Langfuse, `trace_id` прокидывается |
| Минимальные привилегии | `cap-drop ALL`, `no-new-privileges`, read-only rootfs |
| Аудит изменений | Каждый файл фиксируется, кто и когда генерировал |
| Воспроизводимость | Фиксация версии модели, шаблона, зависимостей |

## 10. Уровни готовности выходного пакета

Архитектор не выдаёт «готовый продукт». Он выдаёт **кандидата** с чётким уровнем зрелости.

| Уровень | Название | Что означает | Кто присваивает |
|---|---|---|---|
| 1 | `skeleton` | Структура создана, логика — TODO | Архитектор автоматически |
| 2 | `test-passed` | Тесты проходят, линтер чистый | Архитектор после проверок |
| 3 | `catalog-ready` | Полный пакет, готов к размещению в staging | Архитектор после HITL |
| 4 | `production-approved` | Прошёл пилот, готов к боевой эксплуатации | Человек + CI + пилотные метрики |

**Целевой выход Архитектора в MVP — уровень 3 (`catalog-ready`).**

Уровень 4 присваивается отдельно, после:
- успешного пилота;
- подтверждения метрик `rollout.pilot_metrics`;
- формального утверждения владельцем процесса.

## 12. Обработка ошибок и пограничные случаи

### 12.1. Пользователь не входит в группу `fab-architect`

**Действие:** детерминированный отказ на воркере (§3.7.2). Модель не запускается.

**Ответ пользователю:**
> «У вас нет доступа к Архитектору сценариев. Обратитесь к администратору для включения в группу `fab-architect`.»

**Аудит:** фиксируется отказ, группы пользователя, время.

### 12.2. Пользователь хочет использовать алгоритм, к которому нет доступа

**Действие:** `discover_allowed_assets` не возвращает этот алгоритм. Модель его не видит.

**Если пользователь явно просит:** Архитектор отвечает:
> «Алгоритм `X` не доступен в вашей группе. Доступные альтернативы: ...»

### 12.3. Генерируемый код не проходит тесты 3 раза подряд

**Действие:** остановка. Формирование отчёта:
- Что не работает.
- Какие ошибки.
- Какие попытки были сделаны.
- Рекомендации для ручной доработки.

**Пакет не выдаётся.** Пользователь получает промежуточный результат с пометкой `skeleton`.

### 12.4. Пользователь отклоняет дизайн на этапе утверждения

**Действие:** возврат к `draft_design` с комментариями пользователя. `retry_count` инкрементируется.

### 12.5. Пользователь закрывает вкладку посреди рана

**Действие:** ран продолжает исполнение на воркере (§3.1). Состояние сохраняется в чекпоинтах PostgreSQL. При открытии вкладки — реконнект по `Last-Event-ID` + снапшот из чекпоинта.

### 12.6. Архитектор генерирует код с запрещёнными конструкциями

**Действие:** статический анализ блокирует. Пакет не проходит. Ошибка возвращается в цикл генерации с указанием конкретной строки.

## 13. Интеграция с остальными компонентами платформы

### 13.1. С воркером

Архитектор исполняется как обычный сценарий фабрики. Воркер:
- Ставит задачу через TaskIQ.
- Читает манифест `factory.scenario.architect`.
- Строит allowlist активов.
- Исполняет граф.
- Пишет трейсы в Langfuse.
- Сохраняет чекпоинты в PostgreSQL.

### 13.2. С Gateway

Gateway:
- Принимает `RunAgentInput` от фронтенда.
- Ставит задачу в очередь.
- Ретранслирует события из Redis Streams в SSE.
- Не исполняет граф.

### 13.3. С фронтендом

Фронтенд:
- Подключается к Gateway через `@assistant-ui/react-ag-ui`.
- Рендерит формы утверждения.
- Показывает прогресс.
- Обрабатывает реконнект.

### 13.4. С песочницами

Архитектор использует песочницы для:
- Валидации брифа.
- Линтинга дизайна.
- Запуска тестов.
- Сборки бандла.

Все песочницы — одноразовые, без сети, без секретов.

### 13.5. С каталогом

В MVP Архитектор **не пишет в каталог напрямую**. Он формирует артефакт и передаёт его в зону, откуда оператор или CI может выполнить размещение.

В будущих версиях возможно:
- Автоматическое размещение в `staging` (с аудитом).
- Размещение в `production` через отдельный HITL + CI.

## 14. Что не входит в MVP и почему

| Функция | Почему отложена |
|---|---|
| Прямая запись в production-каталог | Требует дополнительного процесса утверждения и отката |
| Доступ к корпоративным данным (ВМ №4) | Архитектор не знает бизнес-контекст; это задача конкретных сценариев |
| Генерация алгоритмов (не только сценариев) | Отдельный мета-сценарий `factory.algorithm.architect` |
| Автоматическое обновление `scenarios.json` | Требует CI-интеграции |
| Подпись артефактов (cosign) | Требует развёртывания инфраструктуры подписей |
| Генерация A2UI-компонентов | Сложность; в MVP формы фиксированные |
| Мультиязычность | В приоритете русский и английский |
