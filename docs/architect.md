## 1. Идентичность и назначение

### 1.1. Идентификатор

```
ID:          factory.scenario.architect
Kind:        scenario
Version:     0.1.0 (до первого production-прогона)
Owner:       andrei-shaban
Lifecycle:   active
Access:      fab-architect
```

### 1.2. Назначение

Архитектор сценариев — **мета-сценарий**, который превращает процесс создания нового бизнес-сценария из ручной разработки в управляемый конвейер с человеческим контролем.

> Пользователь описывает бизнес-задачу → Архитектор проектирует решение → детерминированные алгоритмы проверяют → человек рецензирует с замечаниями и правками → платформа получает готовый пакет для размещения в каталоге.

Это не «ИИ пишет код за программиста». Это **инструмент снижения порога входа** при сохранении всех гарантий безопасности, изоляции и аудита.

### 1.3. Позиционирование

- Пользователь — не конечный бизнес-оператор, а **внедренец, архитектор или power user**.
- Выход — не бизнес-результат, а **артефакт для каталога фабрики**.
- Качество измеряется не «сколько счетов обработано», а «сколько времени сэкономлено на создании нового сценария».

## 2. Фундаментальные принципы

### 2.1. ИИ предлагает → детерминированные алгоритмы проверяют → человек утверждает

Это главный принцип гибридной архитектуры. Модель никогда не принимает финальных решений о:
- доступе;
- side-effect;
- бизнес-логике;
- регистрации артефактов.

### 2.2. Запрет подмены детерминизма

> Если для бизнес-логики, финансово значимого расчёта или валидации данных отсутствует подходящий детерминированный алгоритм, модель **обязана**:
> 1. **Не выполнять** операцию самостоятельно через генерацию текста.
> 2. **Не аппроксимировать** результат «на глаз».
> 3. **Подсветить пробел** (capability gap) как блокирующую проблему.
> 4. **Предложить варианты**: создать новый алгоритм, форк существующего, или эскалировать человеку.

Это правило защищает финансовую точность, воспроизводимость, аудируемость и доверие бизнеса.

### 2.3. Честность расчётов окупаемости

> Архитектор обязан зафиксировать базовую линию трудозатрат и показателей качества **до** проектирования сценария. Все цифры имеют источник, уверенность и проходят детерминированную проверку реалистичности. Если консервативный сценарий не окупается — Архитектор обязан подсветить это и предложить отказаться от автоматизации.

Никаких «оптимистичных» сценариев. Никаких расчётов «по ощущениям». Никакой манипуляции цифрами.

### 2.4. Расширенное ревью вместо бинарного выбора

> Каждое предложение системы проходит многоуровневую валидацию и предоставляется пользователю не как бинарный выбор «утвердить/отклонить», а как **объект ревью**: с подтверждением, замечаниями, исправлениями, запросом изменений и повторной проверкой.

### 2.5. Генерируемый код — недоверенный

Весь сгенерированный код считается недоверенным до:
- статического анализа;
- валидации манифеста;
- сверки манифест ↔ граф;
- запуска тестов в песочнице;
- HITL-утверждения.

### 2.6. Минимальная осведомлённость модели

Модель видит **только** активы из allowlist (`группы пользователя ∩ access_group`). Манифесты без доступа не подаются и для модели не существуют.

### 2.7. Все циклы ограничены

Максимум 3 итерации на доработку. После — эскалация человеку с полным логом.

## 3. Границы ответственности

### 3.1. Что Архитектор делает

| # | Действие | Результат |
|---|---|---|
| 1 | Проводит структурированное интервью с пользователем | Нормализованный бриф задачи |
| 2 | Фиксирует базовую линию трудозатрат и качества | `baseline` с источниками и уверенностью |
| 3 | Считает ROI в двух сценариях (консервативный + реалистичный) | `roi_scenarios` |
| 4 | Инвентаризирует существующие активы фабрики | Карта переиспользования |
| 5 | Обнаруживает пробелы в детерминированных алгоритмах | `capability_gaps` с вариантами решения |
| 6 | Проектирует граф, манифест, схемы | Утверждённый дизайн |
| 7 | Генерирует код графа на LangGraph | `graph.py` + вспомогательные модули |
| 8 | Генерирует тесты | Golden, selection, unit |
| 9 | Генерирует документацию | README, CHANGELOG, examples |
| 10 | Проверяет пакет детерминированными валидаторами | Отчёт о прохождении/отказе |
| 11 | Запускает тесты в песочнице | Протокол исполнения |
| 12 | Собирает каталожную обёртку | `bundle.json`, `provenance.json`, checksums |
| 13 | Предоставляет HITL-точки для ревью с замечаниями и правками | Лог решений человека |

### 3.2. Что Архитектор НЕ делает и почему

| Запрет | Обоснование |
|---|---|
| Не пишет напрямую в production-каталог | §1 SSOT: принцип автономности артефактов |
| Не обращается к корпоративным данным (ВМ №4) | §3.2 SSOT: доступ только через mTLS воркера с аудитом |
| Не выполняет side-effect операции | §3.7.4 SSOT: только через воркера + HITL + идемпотентность |
| Не изменяет существующие манифесты | §3.7.1 SSOT: пара `(id, version)` immutable |
| Не использует внешние сети | §1 SSOT: Air-Gap, полная автономность |
| Не хранит секреты в генерируемом коде | §3.2 SSOT: секреты не передаются в песочницы |
| Не обходит CI-гейты | §5.5 SSOT: регистрация невозможна без тестов и policy-lint |
| Не внедряет MCP / A2A / WebMCP / Agent Skills | §6 SSOT: статус WATCH |
| Не принимает решение о доступе | §3.7.2 SSOT: доступ применён до модели |
| Не считает ROI «по ощущениям» | Принцип честности расчётов |
| Не выполняет детерминированную логику через LLM | Принцип запрета подмены детерминизма |

### 3.3. Антипаттерны, которые Архитектор предотвращает

| Антипаттерн | Как предотвращается |
|---|---|
| Сценарий без `when_not_to_use` | Policy-lint блокирует регистрацию |
| Все алгоритмы в одном графе без переиспользования | Принудительный поиск существующих активов |
| Модель видит весь каталог | `discover_allowed_assets` строит allowlist до контекста |
| Побочный эффект без HITL | Граф не генерируется без ноды `hitl` перед `side-effect` |
| Тесты написаны «на глаз» | Генерируются структурированные golden/selection наборы |
| Версии «возьмём последнюю» | Манифест требует точных `ref@version` |
| Модель считает НДС «на глаз» | Обнаружение capability gap → предложение создать алгоритм |
| ROI без базовой линии | Блок `baseline` обязателен в брифе |
| Пользователь не может оставить замечание | Расширенная HITL-валидация |

## 4. Пользовательский путь (пошагово)

### 4.1. Этап 1: Входной запрос

Пользователь приходит с неструктурированным описанием:

> «Мне нужен сценарий обработки входящих договоров: загрузить файл, распознать, извлечь реквизиты, сравнить с шаблоном, показать отличия менеджеру, после подтверждения создать черновик в учётной системе.»

Архитектор **не начинает генерировать код**. Он начинает интервью.

### 4.2. Этап 2: Структурированное интервью

Архитектор задаёт вопросы по фиксированному чек-листу:

**Бизнес-контекст:**
- Какая задача решается?
- Кто инициирует процесс?
- Кто утверждает результат?
- Какой объём операций в день/неделю?
- Какие системы затронуты?

**Данные:**
- Какие входные данные (формат, источник)?
- Какие выходные данные (формат, потребитель)?
- Есть ли мастер-данные, справочники?
- Нужен ли доступ к корпоративным реестрам?

**Управление:**
- Нужны ли точки человеческого контроля?
- Какие решения принимает человек?
- Какой горизонт паузы (дни, недели)?
- Что происходит при отказе?

**Безопасность и доступ:**
- Кто имеет право запускать сценарий?
- Какие группы доступа?
- Есть ли чувствительные данные?

**Интеграции:**
- Какие внешние системы?
- Какой протокол (mTLS, API, файл)?
- Есть ли идемпотентность на стороне целевой системы?

Результат этапа: **нормализованный бриф** — структурированный JSON, соответствующий схеме `schemas/brief.json`.

### 4.3. Этап 3: Фиксация базовой линии (ОБЯЗАТЕЛЬНО)

Архитектор **обязан** зафиксировать текущее состояние процесса до автоматизации:

```yaml
baseline:
  operator_time_minutes_per_case:
    value: 25
    unit: minutes
    source: operator_interview    # interview | timesheet | crm | estimate
    confidence: high              # high | medium | low
  
  cases_per_period:
    value: 120
    period: week                  # day | week | month
    source: crm
    confidence: high
  
  operators_count:
    value: 3
    source: process_owner
    confidence: high
  
  error_rate_percent:
    value: 8.0
    source: quality_report
    confidence: medium
  
  avg_rework_minutes_per_error:
    value: 40
    source: estimate
    confidence: low
  
  sla_breach_rate_percent:
    value: 12.0
    source: monitoring
    confidence: high
  
  direct_cost_per_case_rub:
    value: 450
    source: finance
    confidence: medium
```

Если пользователь не может дать точных цифр:
- Архитектор помогает оценить через уточняющие вопросы.
- Предлагает диапазоны.
- Просит указать источник оценки.
- При отсутствии данных помечает как «оценочный» и требует валидации владельцем процесса.

**Без базовой линии проектирование не начинается.**

### 4.4. Этап 4: Расчёт ROI

Архитектор считает **два** сценария ROI:

**Консервативный** (минимальный эффект):
- -50% времени оператора
- -60% ошибок
- Окупаемость: 8 месяцев

**Реалистичный** (ожидаемый эффект):
- -70% времени
- -80% ошибок
- Окупаемость: 4 месяцев

Никаких «оптимистичных» сценариев.

Если консервативный сценарий не окупается (окупаемость > 18 месяцев) — Архитектор **обязан** подсветить это и предложить отказаться от автоматизации.

### 4.5. Этап 5: Утверждение базовой линии и ROI (HITL)

Пользователь видит:

```
📊 Базовая линия и ожидаемый эффект

Текущее состояние:
  • 120 операций в неделю × 25 минут = 50 часов/неделю
  • 3 оператора, загруженность 80%
  • 8% ошибок → ~38 переделок/месяц
  
Ожидаемый эффект (консервативно):
  • -50% времени → 25 часов/неделю
  • -60% ошибок → ~15 переделок/месяц
  • Окупаемость: 8 месяцев
  
Ожидаемый эффект (реалистично):
  • -70% времени → 15 часов/неделю
  • -80% ошибок → ~8 переделок/месяц
  • Окупаемость: 4 месяца

⚠️ Предупреждения:
  • Среднее время переделки (40 мин) — оценка без замера.
    Требуется фактический замер до старта пилота.

[Утвердить] [Скорректировать базовую] [Отказаться от автоматизации]
```

Кнопка **«Отказаться от автоматизации»** — важная часть. Архитектор даёт человеку сказать: «По этим цифрам автоматизировать не стоит».

### 4.6. Этап 6: Инвентаризация активов

Архитектор вызывает детерминированный алгоритм `architect.discover_allowed_assets`:

1. Читает in-memory индекс манифестов (§3.7.1 SSOT).
2. Фильтрует по `группы пользователя ∩ access_group`.
3. Возвращает **только разрешённые** активы.

Результат:

```json
{
  "available_algorithms": [
    {"id": "finance.invoice.totals", "version": "1.3.0", "class": "pure"},
    {"id": "ocr.paddle.batch", "version": "1.2.0", "class": "pure"}
  ],
  "available_tools": [
    {"id": "notify.operator", "version": "1.0.0"}
  ],
  "missing_capabilities": [
    "Распознавание договоров (нет существующего алгоритма)"
  ]
}
```

### 4.7. Этап 7: Обнаружение пробелов детерминизма

Архитектор анализирует требования брифа и сопоставляет их с доступными активами.

Если для какого-то шага графа нужен детерминированный алгоритм, но его нет, формируется запись:

```json
{
  "capability_gap": {
    "required_for": "Расчёт итогов по договорам с плавающей ставкой",
    "expected_class": "pure",
    "expected_execution": "sandbox",
    "reason": "Существующий finance.invoice.totals@1.3.0 не поддерживает плавающие ставки и многовалютность",
    "similar_assets": [
      {"id": "finance.invoice.totals", "version": "1.3.0", "similarity": 0.72}
    ],
    "options": [
      {
        "type": "fork",
        "target": "finance.invoice.totals",
        "target_version": "1.3.0",
        "new_version": "2.0.0",
        "changes": "Добавить поддержку плавающих ставок и многовалютности",
        "breaking_change": true,
        "supersedes": "finance.invoice.totals@1.3.0"
      },
      {
        "type": "new",
        "proposed_id": "finance.contract.floating_totals",
        "version": "0.1.0",
        "class": "pure",
        "execution": "sandbox"
      },
      {
        "type": "escalate",
        "reason": "Требует уточнения бизнес-правил у владельца процесса"
      }
    ]
  }
}
```

### 4.8. Этап 8: Разрешение пробелов (HITL)

Пользователь видит:

```
⚠️ Обнаружен пробел в детерминированных алгоритмах

Для узла «Расчёт итогов по договорам» требуется детерминированный алгоритм, 
но подходящий отсутствует в каталоге.

Существующий кандидат: finance.invoice.totals@1.3.0 — не поддерживает 
плавающие ставки.

Варианты решения:
1. 🔀 Форк finance.invoice.totals → версия 2.0.0 (ломающее изменение, supersedes)
2. ➕ Создать новый finance.contract.floating_totals@0.1.0
3. ⏸️ Эскалировать владельцу процесса для уточнения правил

Без решения этого пробела сценарий не может быть зарегистрирован.

[Выбрать вариант] [Уточнить детали]
```

### 4.9. Этап 9: Проектирование дизайна

Архитектор генерирует **черновик дизайна**:

- Список узлов графа (тип, ref, назначение).
- Рёбра и условия ветвления.
- Точки HITL.
- Схемы состояния.
- Требования к GPU, корпоративным данным, инструментам.
- Группа доступа.
- `when_to_use` / `when_not_to_use`.

Дизайн проверяется детерминированным линтером (`architect.policy_lint_design`).

### 4.10. Этап 10: Ревью дизайна (HITL с замечаниями)

Пользователь видит не просто кнопку «Утвердить», а полноценную форму ревью:

- Визуализацию графа (узлы, рёбра, условия).
- Манифест в YAML.
- Список переиспользованных активов.
- Список новых компонентов.
- Предупреждения линтера.
- Уровень уверенности (`validated` / `needs_review` / `incomplete`).

**Кнопки:**
- Утвердить
- Утвердить с комментарием
- Запросить изменения
- Внести правку
- Отклонить
- Эскалировать
- Запросить объяснение

Пользователь может:
- Оставить информационный комментарий (не блокирует).
- Оставить блокирующее замечание (требует доработки).
- Внести локальное исправление (правит поле напрямую).

### 4.11. Этап 11: Применение замечаний и повторная валидация

Если пользователь запросил изменения или внёс правки:

1. Архитектор фиксирует объект изменения.
2. Определяет затронутые объекты.
3. Выполняет локальную перегенерацию (не полную).
4. Повторно запускает все валидации.
5. Показывает пользователю обновлённый результат.

**Нельзя показать «исправлено», если повторные проверки не пройдены.**

### 4.12. Этап 12: Генерация пакета

После утверждения дизайна Архитектор генерирует:

```
<scenario-id>/<version>/
  manifest.yaml          ← канон, источник истины
  graph.py               ← исполнимая реализация на LangGraph
  schemas/
    input.json           ← схема входа
    state.json           ← схема состояния графа
    output.json          ← схема выхода
    errors.json          ← схема ошибок
  nodes/                 ← вспомогательные модули
  tests/
    golden/              ← эталонные пары вход→выход
    selection/           ← запросы для проверки выбора (≥10)
    unit/                ← модульные тесты
  examples/              ← примеры запросов
  README.md              ← описание, инструкция, ограничения
  CHANGELOG.md           ← история версий
  bundle.json            ← каталожная обёртка
  provenance.json        ← кто, когда, какая модель, какой шаблон
  checksums.txt          ← SHA-256 всех файлов
  license.spdx           ← лицензия
  notice.txt             ← атрибуция
```

### 4.13. Этап 13: Валидация и тестирование

Сгенерированный пакет проходит конвейер проверок:

```
Статический анализ (AST)
  → Запрещённые импорты?
  → Хардкод секретов?
  → Сетевые вызовы?
  → Динамический exec/eval?
  
Валидация манифеста
  → Схема §3.7.4 корректна?
  → Все обязательные поля заполнены?
  
Сверка манифест ↔ граф
  → Узлы совпадают?
  → Рёбра совпадают?
  → Предикаты валидны?
  
Запуск в песочнице (gVisor)
  → runsc, --network none, read-only rootfs
  → Golden tests passed?
  → Unit tests passed?
  → Selection tests accuracy ≥ 95%?
  
Policy-lint
  → Все правила §3.7.3–§3.7.7 соблюдены?
```

Если проверки не пройдены — Архитектор возвращается к генерации с указанием конкретных ошибок. Максимум 3 итерации.

### 4.14. Этап 14: Ревью пакета (HITL с замечаниями)

Пользователь видит:

- Список файлов с размерами и digest.
- Diff по каждому файлу.
- Результаты тестов.
- Предупреждения.
- Уровень уверенности.

**Кнопки:** те же, что на этапе ревью дизайна.

### 4.15. Этап 15: Финализация

Если пакет принят:

1. Формируется `bundle.json` с полными метаданными.
2. Считаются digest всех файлов.
3. Записывается `provenance.json`.
4. Готовится patch для `scenarios.json`.
5. Пакет передаётся в staging-каталог.

**В MVP запись в production-каталог не выполняется.** Только формирование артефакта.

## 5. Граф сценария

### 5.1. Полная структура

```
intake
  → clarify
  → normalize_brief              [algorithm, pure, sandbox]
  → collect_baseline             [llm]
  → calculate_roi                [algorithm, pure, sandbox]
  → validate_roi                 [algorithm, pure, sandbox]
  → roi_approval                 [hitl, form: a2ui/roi_review]
  → discover_allowed_assets      [algorithm, corp-read, worker]
  → analyze_capability_gaps      [algorithm, pure, sandbox]
  → resolve_gaps                 [hitl, form: a2ui/capability_gap]
  → draft_design                 [llm]
  → lint_design                  [algorithm, pure, sandbox]
  → review_design                [hitl, form: a2ui/design_review]
  → apply_design_feedback        [algorithm, pure, sandbox]
  → revalidate_design            [algorithm, pure, sandbox]
  → generate_code                [llm]
  → scaffold_files               [tool, sandbox]
  → run_sandbox_tests            [algorithm, worker]
  → review_package               [hitl, form: a2ui/package_review]
  → apply_package_feedback       [algorithm, pure, sandbox]
  → revalidate_package           [algorithm, pure, sandbox]
  → finalize_bundle              [algorithm, pure, sandbox]
  → emit_artifact                [tool, worker]
```

### 5.2. Ветвления и возвраты

```yaml
# ROI
- from: validate_roi
  to: roi_approval
  if: state.roi.conservative.recommendation == "reconsider"

- from: validate_roi
  to: discover_allowed_assets
  if: state.roi.conservative.recommendation == "proceed_to_pilot"

- from: roi_approval
  to: END
  if: state.roi_approval.decision == "reject_automation"

- from: roi_approval
  to: discover_allowed_assets
  if: state.roi_approval.decision in ["approve", "approve_with_comment"]

# Capability gaps
- from: analyze_capability_gaps
  to: resolve_gaps
  if: state.capability_gaps.length > 0

- from: analyze_capability_gaps
  to: draft_design
  if: state.capability_gaps.length == 0

- from: resolve_gaps
  to: draft_design
  if: state.gaps_resolved == true

- from: resolve_gaps
  to: END
  if: state.gaps_resolved == false && state.escalated == true

# Design review
- from: review_design
  to: apply_design_feedback
  if: state.review.decision in ["request_changes", "edit", "reject"]

- from: review_design
  to: generate_code
  if: state.review.decision in ["approve", "approve_with_comment"]

- from: apply_design_feedback
  to: revalidate_design

- from: revalidate_design
  to: review_design
  if: state.revalidation.required_human_review == true

- from: revalidate_design
  to: generate_code
  if: state.revalidation.passed == true

# Package review
- from: run_sandbox_tests
  to: review_package
  if: state.tests_passed == true

- from: run_sandbox_tests
  to: generate_code
  if: state.tests_passed == false && state.fix_attempts < 3

- from: review_package
  to: apply_package_feedback
  if: state.review.decision in ["request_changes", "edit", "reject"]

- from: review_package
  to: finalize_bundle
  if: state.review.decision in ["approve", "approve_with_comment"]

- from: apply_package_feedback
  to: revalidate_package

- from: revalidate_package
  to: review_package
  if: state.revalidation.required_human_review == true

- from: revalidate_package
  to: finalize_bundle
  if: state.revalidation.passed == true
```

**Все циклы ограничены.** После 3 попыток — остановка с полным логом и эскалация.

## 6. Детализация ключевых алгоритмов

### 6.1. `architect.normalize_brief`

**Назначение:** превратить свободный текст пользователя в структурированный бриф.

**Вход:**
```json
{
  "raw_text": "string",
  "interview_answers": {...}
}
```

**Выход:** нормализованный бриф по схеме `schemas/brief.json`.

**Ограничения:** `class: pure`, `execution: sandbox`.

### 6.2. `architect.calculate_roi`

**Назначение:** детерминированно посчитать базовую линию и два сценария ROI.

**Вход:**
- `baseline` из брифа.
- Стоимость часа оператора.
- Стоимость часа разработки/внедрения.

**Выход:**
```json
{
  "monthly_hours_spent_now": 120,
  "monthly_errors_count": 38,
  "monthly_direct_cost_rub": 216000,
  
  "scenarios": {
    "conservative": {
      "monthly_hours_saved": 60,
      "monthly_cost_saved_rub": 108000,
      "breakeven_months": 8,
      "recommendation": "proceed_to_pilot"
    },
    "realistic": {
      "monthly_hours_saved": 84,
      "monthly_cost_saved_rub": 151000,
      "breakeven_months": 4,
      "recommendation": "proceed_to_pilot"
    }
  },
  
  "warnings": [...],
  "proceed_recommended": true
}
```

### 6.3. `architect.validate_roi_realism`

**Назначение:** проверить реалистичность заявленных улучшений.

**Проверяет:**
- Заявленное улучшение не превышает 95% без обоснования.
- Срок окупаемости ≤ 18 месяцев (иначе предупреждение).
- Срок окупаемости ≤ 36 месяцев (иначе блок).
- Все цифры имеют источник и уверенность.
- Низкоуверенные данные помечены для HITL.

### 6.4. `architect.discover_allowed_assets`

**Назначение:** найти переиспользуемые активы, доступные текущему пользователю.

**Критическое требование (§3.7.2 SSOT):** модель не принимает решение о доступе — доступ применён до неё.

Алгоритм выполняется **на воркере**, читает in-memory индекс манифестов, фильтрует по группам пользователя.

### 6.5. `architect.analyze_capability_gaps`

**Назначение:** обнаружить пробелы в детерминированных алгоритмах.

**Логика:**
1. Из брифа извлекаются требования к детерминированным операциям.
2. Каждая операция сопоставляется с доступными алгоритмами.
3. Если совпадение < порога (0.85) или отсутствует требуемая функциональность — фиксируется пробел.
4. Для каждого пробела генерируются варианты: форк, новый, эскалация.

### 6.6. `architect.policy_lint_design`

**Назначение:** проверить черновик дизайна до утверждения человеком.

**Проверяет:**

| Правило | Источник в SSOT |
|---|---|
| `execution: sandbox` ⇒ `class: pure` | §3.7.3 |
| `class: corp-read` ⇒ воркер + mTLS | §3.7.3 |
| `class: side-effect` ⇒ HITL выше по графу | §3.7.4 |
| `class: side-effect` ⇒ идемпотентность | §3.7.4 |
| `interrupt()` в отдельной ноде | §3.1 |
| Блок для модели ≤ 512 токенов | §3.7.5 |
| Все `ref` — точные версии | §3.7.1 |
| Рёбра манифеста ⊆ рёбра графа | §3.7.4 |
| `when_not_to_use` не пустой | §3.7.5 |
| `baseline` присутствует | Новый принцип |
| `roi` имеет conservative сценарий | Новый принцип |
| Нет LLM для детерминированной логики | Новый принцип |

### 6.7. `architect.apply_review_feedback`

**Назначение:** принять замечания и правки пользователя, нормализовать их, определить затронутые объекты, сформировать задание на локальную перегенерацию.

**Вход:**
```json
{
  "review_decision": {
    "type": "request_changes",
    "comments": ["Добавить проверку лимита перед созданием документа"],
    "requested_changes": [...],
    "manual_edits": []
  }
}
```

**Выход:**
```json
{
  "affected_objects": ["manifest.composition", "graph.py", "tests/unit"],
  "regeneration_scope": "partial",
  "validation_required": true,
  "blocked": false
}
```

### 6.8. `architect.revalidate_artifacts`

**Назначение:** повторно проверить изменённые артефакты, сверить с инвариантами SSOT, определить, нужен ли повторный HITL.

**Выход:**
```json
{
  "passed": false,
  "errors": [],
  "warnings": ["Добавленный узел требует нового детерминированного алгоритма"],
  "requires_human_review": true,
  "requires_capability_gap_resolution": true
}
```

### 6.9. `architect.sandbox_validator`

**Назначение:** запустить сгенерированные тесты в изолированной среде.

**Параметры песочницы:**
- `runsc` (gVisor)
- `--network none`
- `--read-only`
- `--tmpfs /tmp`
- `--cap-drop ALL`
- `--no-new-privileges`
- `--memory 512m`
- `--pids-limit 64`
- `--timeout 60s`

### 6.10. `architect.bundle_assembler`

**Назначение:** собрать финальную обёртку пакета.

**Формирует:** `bundle.json`, `provenance.json`, `checksums.txt`.

## 7. Расширенная HITL-валидация

### 7.1. Модель решения

Вместо `approved == true/false`:

```yaml
decision:
  type: approve | approve_with_comment | request_changes | edit | reject | escalate | explain
  reason: string
  comments: []
  requested_changes: []
  manual_edits: {}
  target_objects: []
  force_override: false
```

### 7.2. Типы замечаний

**Информационный комментарий:** не блокирует утверждение. Сохраняется в аудит.

**Блокирующее замечание:** требует доработки. Текущий этап не утверждается.

**Локальное исправление:** пользователь сам правит объект. Проходит повторную валидацию.

### 7.3. Объекты ревью

| Объект | Что можно проверять и править |
|---|---|
| Бизнес-бриф | Цель, вход, выход, роли, ограничения |
| Базовая линия | Трудозатраты, источники, уверенность |
| ROI | Сценарии, целевые улучшения |
| Список активов | Правильность переиспользования |
| Пробелы | Корректность определения отсутствия алгоритма |
| Дизайн графа | Узлы, рёбра, условия, HITL-точки |
| Манифест | `id`, `version`, `access_group`, `when_to_use`, `when_not_to_use`, SLA |
| Схемы | `input`, `output`, `state`, `errors` |
| Код графа | `graph.py`, вспомогательные модули |
| Тесты | Полнота golden, selection, unit |
| README | Описание, ограничения, инструкция |
| Итоговый пакет | Состав файлов, digest, метаданные |

### 7.4. Уровни уверенности

| Уровень | Когда показывается |
|---|---|
| `validated` | Все проверки пройдены |
| `needs_review` | Есть предупреждения |
| `incomplete` | Не хватает данных |
| `capability_gap` | Нет детерминированного алгоритма |
| `risky` | Есть side-effect, доступ к корп. данным |
| `blocked` | Есть блокирующие ошибки |

## 8. Подпроцессы

### 8.1. Создание нового алгоритма

Если пользователь выбрал «создать новый» при разрешении capability gap:

1. Сформировать черновик манифеста алгоритма по §3.7.3 SSOT.
2. Сгенерировать код (детерминированный, без LLM внутри).
3. Сгенерировать схемы I/O.
4. Сгенерировать тесты (golden, selection).
5. Проверить в песочнице.
6. Утвердить с пользователем (HITL).
7. Зарегистрировать как зависимость нового сценария.

**Важно:** сам алгоритм не содержит LLM-вызовов. Он детерминированный. LLM используется только для генерации его кода и тестов на этапе разработки.

### 8.2. Форк существующего алгоритма

Если выбран форк:

1. Прочитать манифест и код существующего алгоритма.
2. Определить delta-изменения.
3. Создать новую мажорную версию (пара `(id, version)` immutable).
4. Установить `supersedes` на старую версию.
5. Сгенерировать обновлённый код и тесты.
6. Проверить обратную совместимость.
7. Утвердить с пользователем.

## 9. Безопасность генерируемого кода

### 9.1. Статический анализ (до запуска)

**Запрещено:**
```python
# Сеть
import socket, http.client, urllib, requests, httpx, aiohttp

# Файловая система за пределами /tmp
open('/etc/...'), open('/root/...'), open('/home/...')

# Секреты
os.environ['SECRET'], os.getenv('TOKEN')

# Динамический код
eval(), exec(), compile(), __import__()

# Подпроцессы
subprocess, os.system, os.popen

# Сериализация с кодом
pickle, marshal, shelve
```

### 9.2. Изоляция исполнения

Весь сгенерированный код исполняется в песочнице с параметрами §3.2 SSOT.

### 9.3. Зависимости

Сгенерированный код не может устанавливать пакеты из интернета. Допустимые зависимости — только из внутреннего зеркала PyPI через предзапечённый wheel-cache с хешами.

### 9.4. Запрет на секреты

В генерируемом коде **не должно быть** токенов, паролей, приватных ключей, путей к сертификатам, адресов внутренних сервисов.

- Уровень уверенности.
- Поле для замечаний пользователя.
- Возможность править отдельные поля.

**Состав:**
- Список файлов с размерами и digest.

## 13. Обработка ошибок и пограничные случаи

### 13.1. Пользователь не входит в группу `fab-architect`

**Действие:** детерминированный отказ на воркере (§3.7.2 SSOT). Модель не запускается.

**Ответ:** «У вас нет доступа к Архитектору сценариев. Обратитесь к администратору.»

### 13.2. Пользователь хочет использовать алгоритм, к которому нет доступа

**Действие:** `discover_allowed_assets` не возвращает этот алгоритм. Модель его не видит.

**Если пользователь явно просит:** «Алгоритм `X` не доступен в вашей группе. Доступные альтернативы: ...»

### 13.3. Пользователь не может дать точные цифры базовой линии

**Действие:** Архитектор помогает оценить через уточняющие вопросы, предлагает диапазоны, помечает как `confidence: low`, требует валидации владельцем процесса.

### 13.4. Консервативный ROI не окупается

**Действие:** Архитектор показывает предупреждение, предлагает отказаться от автоматизации или пересмотреть базовую линию.

### 13.5. Генерируемый код не проходит тесты 3 раза подряд

**Действие:** остановка. Формирование отчёта с указанием, что не работает, какие ошибки, какие попытки были сделаны, рекомендации для ручной доработки. Пакет не выдаётся.

### 13.6. Пользователь отклоняет дизайн на этапе ревью

**Действие:** возврат к `draft_design` с комментариями пользователя. `retry_count` инкрементируется.

### 13.7. Пользователь закрывает вкладку посреди рана

**Действие:** ран продолжает исполнение на воркере (§3.1 SSOT). Состояние сохраняется в чекпоинтах PostgreSQL. При открытии вкладки — реконнект по `Last-Event-ID` + снапшот из чекпоинта.

### 13.8. Пользовательская правка нарушает инвариант SSOT

**Действие:** система показывает конфликт, объясняет правило, предлагает безопасную альтернативу. Не применяет изменение без явного допустимого обхода. Если обход невозможен — блокирует.

**Запрещено принимать без проверки:**
- изменение `execution` на небезопасное;
- удаление HITL перед `side-effect`;
- удаление идемпотентности;
- использование LLM вместо детерминированного алгоритма;
- назначение недоступной группы доступа;
- указание несуществующей версии алгоритма;
- удаление обязательных тестов;
- отключение аудита;
- добавление сетевых вызовов в песочницу;
- изменение `(id, version)` существующего артефакта.

## 14. Уровни готовности выходного пакета

| Уровень | Название | Что означает | Кто присваивает |
|---|---|---|---|
| 1 | `skeleton` | Структура создана, логика — TODO | Архитектор автоматически |
| 2 | `test-passed` | Тесты проходят, линтер чистый | Архитектор после проверок |
| 3 | `catalog-ready` | Полный пакет, готов к размещению в staging | Архитектор после HITL |
| 4 | `production-approved` | Прошёл пилот, готов к боевой эксплуатации | Человек + CI + пилотные метрики |

**Целевой выход Архитектора в MVP — уровень 3 (`catalog-ready`).**

## 15. Интеграция с платформой

### 15.1. С воркером

Архитектор исполняется как обычный сценарий фабрики. Воркер:
- Ставит задачу через TaskIQ.
- Читает манифест `factory.scenario.architect`.
- Строит allowlist активов.
- Исполняет граф.
- Пишет трейсы в Langfuse.
- Сохраняет чекпоинты в PostgreSQL.

### 15.2. С Gateway

Gateway:
- Принимает `RunAgentInput` от фронтенда.
- Ставит задачу в очередь.
- Ретранслирует события из Redis Streams в SSE.
- Не исполняет граф.

### 15.3. С фронтендом

Фронтенд:
- Подключается к Gateway через `@assistant-ui/react-ag-ui`.
- Рендерит формы ревью.
- Показывает прогресс.
- Обрабатывает реконнект.

### 15.4. С песочницами

Архитектор использует песочницы для:
- Валидации брифа.
- Расчёта ROI.
- Линтинга дизайна.
- Запуска тестов.
- Сборки бандла.

Все песочницы — одноразовые, без сети, без секретов.

### 15.5. С каталогом

В MVP Архитектор **не пишет в каталог напрямую**. Он формирует артефакт и передаёт его в зону, откуда оператор или CI может выполнить размещение.

---

## 16. Что не входит в MVP

| Функция | Почему отложена |
|---|---|
| Прямая запись в production-каталог | Требует дополнительного процесса утверждения и отката |
| Доступ к корпоративным данным (ВМ №4) | Архитектор не знает бизнес-контекст |
| Генерация алгоритмов (не только сценариев) | Отдельный мета-сценарий `factory.algorithm.architect` |
| Автоматическое обновление `scenarios.json` | Требует CI-интеграции |
| Подпись артефактов (cosign) | Требует развёртывания инфраструктуры подписей |
| Генерация A2UI-компонентов | Сложность; в MVP формы фиксированные |
| Мультиязычность | В приоритете русский и английский |

## 19. Предлагаемые правки для SSOT (отложены до команды)

Следующие изменения предлагаются для включения в Production Blueprint v5.2.1:

### §1 (Ключевые архитектурные принципы)

Дополнить принцип «Архитектура Фабрики»:

> **Запрет подмены детерминизма.** Если для бизнес-логики, финансово значимого расчёта или валидации данных отсутствует подходящий детерминированный алгоритм, модель обязана подсветить пробел и предложить создание нового алгоритма или форк существующего. Выполнение детерминированных операций средствами LLM запрещено и блокируется policy-линтом.

> **Честность расчётов окупаемости.** Архитектор обязан зафиксировать базовую линию трудозатрат и показателей качества до проектирования сценария. Все цифры имеют источник, уверенность и проходят детерминированную проверку реалистичности. Если консервативный сценарий не окупается — Архитектор обязан подсветить это и предложить отказаться от автоматизации.

### §3.7.4 (Манифест сценария — состав)

Расширить блок `rollout`:

```yaml
rollout:
  baseline:
    operator_time_minutes_per_case: {value, unit, source, confidence}
    cases_per_period: {value, period, source, confidence}
    error_rate_percent: {value, source, confidence}
    sla_breach_rate_percent: {value, source, confidence}
  
  target_improvements:
    operator_time_reduction_percent: {target, min_acceptable}
    error_rate_reduction_percent: {target, min_acceptable}
    sla_breach_reduction_percent: {target, min_acceptable}
  
  pilot_metrics: [...]
  pilot_duration_days: 30
  go_no_go_threshold: min_acceptable
  
  roi_scenarios:
    conservative: {breakeven_months, confidence}
    realistic: {breakeven_months, confidence}
```

### §3.7.5 (Требования к блоку для модели)

Добавить:

> **Обязанность обнаружения пробелов.** Блок для модели должен содержать явную инструкцию: при отсутствии подходящего детерминированного алгоритма — не выполнять операцию, а сформировать `capability_gap` с вариантами решения (новый алгоритм, форк, эскалация).

### §3.7.7 (Оценка и CI-гейты)

Добавить новые гейты:

> **Гейт детерминизма.** Регистрация сценария невозможна, если узлы с бизнес-логикой, финансовыми расчётами или валидацией данных не ссылаются на детерминированные алгоритмы или инструменты. Использование `type: llm` для таких узлов блокируется.

> **Гейт базовой линии.** Регистрация сценария невозможна без блока `baseline` с источниками и уверенностью.

> **Гейт реалистичности ROI.** Консервативный сценарий ROI обязателен. Срок окупаемости > 36 месяцев блокирует регистрацию.

### §5.6 (Приёмочные сценарии)

Добавить:

> [ ] Сценарий требует расчёта, для которого нет алгоритма → модель подсвечивает пробел, предлагает форк/создание, не выполняет расчёт сама.
> [ ] Попытка зарегистрировать сценарий с LLM-узлом вместо детерминированного алгоритма для бизнес-логики → CI-гейт блокирует регистрацию.
> [ ] Сценарий без базовой линии → CI-гейт блокирует регистрацию.
> [ ] Пользователь вносит правку в манифест → система выполняет повторную валидацию.
> [ ] Пользовательская правка нарушает инвариант SSOT → система блокирует и объясняет правило.
